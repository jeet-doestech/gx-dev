Quality control

Gates & escalation

Gates promote work on evidence, never confidence. The test gate verifies behavior; the review gate assumes green tests can still hide defects; five consecutive failures force holistic replanning.

Test gateOwnership routingReview gateEscalationEvidence
Gate one

Integrated test gate

Code and tests meet for the first time in the staging worktree, where verification is executed deterministically and recorded exactly.

Preflight checks

  • Meaningful implementation exists — no stub-only diffs.
  • Promised tests are present and enabled.
  • No constant-only or vacuous assertions.
  • No secrets, conflict markers, or unrelated changes.
  • No accidental vendor or generated files.

Command allowlist

Only allowlisted verification commands execute. The allowlist is assembled from project manifests, CI configuration, and user settings; anything outside it must be discovered, justified, and recorded first.

  • Exact argv, environment summary, and exit code persisted.
  • Destructive and network commands denied by default.
  • Output truncated in-place, archived in full as evidence.

Deterministic execution

  • Developer and test branches integrate into staging.
  • Only mechanical conflicts resolve automatically.
  • Project-native discovery: package scripts, Makefiles, CI steps.
  • Valid tests are never weakened or deleted to obtain a pass.
  • Every code-changing repair invalidates prior assurance.
Routing

Failures go to the responsible owner

Gate two

Adversarial review severity model

The reviewer inspects the combined staged diff for correctness, security, data loss, performance, test quality, and hidden coupling — and returns severity-ranked findings with paths, lines, evidence, and remediation.

SeverityEffect in v1Disposition
BlockingGate fails; promotion is blockedMust be fixed. Only explicit user authority may accept material residual risk.
MajorBlocks in v1Treated as blocking: fix, or escalate the decision to the user.
MinorAdvisoryRecorded in evidence and batched as follow-up work.
InfoAdvisoryLogged for context; never blocks.
Reviewers cannot waive blocking findings. Developer and reviewer may not negotiate acceptance privately; documentation updates begin only after the review gate passes.
Escalation

Five failures force holistic replanning

Each gate keeps its own consecutive-failure counter. A pass resets only its own counter; infrastructure retries never count as code or test failures.

Auditability

Evidence requirements per outcome

Every gate verdict cites its evidence. Nothing is trusted because an agent asserted it.

On pass

  • Exact verification commands, environment, and exit codes.
  • Integrated staging revision hash under test.
  • Review findings with severities and their resolutions.
  • Documentation diff verified against actual behavior.
  • Gate verdict record with requirement, plan, and evidence hashes.

On fail

  • Failing command, exit code, and archived output reference.
  • Minimal reproduction and the requirement it violates.
  • Ownership classification: developer, test writer, both, or infrastructure.
  • Attempt record: input revision hashes, changed files, responsible agent, proposed root cause, action taken, resulting state.
  • Preserved evidence links — the causal history the planner will receive.
Never discard history. After five consecutive failures the planner receives the complete failure record; local repair stops before context is lost.
