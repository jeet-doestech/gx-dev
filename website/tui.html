Command surface

The /gx-dev command set

All commands are namespaced under /gx-dev and operate on the currently selected run unless a run id is given.

Per-subagent models

The model picker

/gx-dev models sets the model for each of the seven subagents — researcher, planner, developer, testWriter, testRunner, reviewer, committer — from your own pi setup. Model discovery is registry-first: candidates come from pi's model registry, with a CLI fallback (pi --list-models) when the registry is unavailable. Unmatched picks warn but never block — see troubleshooting.

Rolespick one of the seven
Modelsregistry list · thinking badges · inherit · clear override
Thinkingoff → max, when supported
Persistedatomic write to config.json
Rebuiltengine rebuilt for the next spawn

In the model list

  • Each candidate shows its thinking levels as badges, so the model and the reasoning budget are chosen together.
  • inherit delegates the role to the session's default model — the child is spawned without --model.
  • A clear override entry removes the role's key so the package pin or built-in default applies again.

On save

  • The selection is persisted to agents.models.<role> in .gx-dev/config.json with an atomic write.
  • The engine is rebuilt immediately, so the next dispatch of that role uses the new model — no restart needed.
  • Prefer the shell? scripts/models.mjs show|list|set|unset|get drives the same store — see configuration.

Compact workflow widget

Above the editor, a one-line widget mirrors the canonical path and highlights the active state, mirroring the state graph without opening the dashboard.

Both widgets render through pi's theme-aware renderers: no hard-coded colors, native light and dark operation.

Human authority

Modal question flow

Material decisions surface as a modal; minor reversible ones are answered by the orchestrator and logged.

Raisedambiguity found
Classifiedminor vs material
Modalcontext + options
Answereduser decides
Recordedhash-linked approval
Resumedstate continues

What the modal shows

  • The question, with the material decision stated plainly.
  • Linked artifacts: requirements, plan sections, evidence.
  • Available options and their consequences.
  • Which checkpoint this satisfies.

Rules

  • Answers are persisted with artifact hashes before work resumes.
  • Stale approvals cannot be reused against changed inputs.
  • An absent user moves the run to WAITING_FOR_USER, checkpointed and resumable.
  • Every question and answer appears in /gx-dev history.
