state.json fields

Agent completion JSON

Every agent returns validated structured output through a dedicated completion tool. Invalid output is retried once with schema feedback, then treated as an agent failure.

{
  "status": "complete",
  "summary": "...",
  "artifacts": ["..."],
  "questions": [],
  "assumptions": [],
  "risks": [],
  "recommendedNextState": "PLAN"
}

Base schema, common to all roles.

Evidence directory layout

Raw evidence is append-only and content-addressed where practical. Capture is not automatically memory.

.gx-dev/runs/<run-id>/evidence/
├── user-input/
├── web/
├── agent-output/
├── commands/
├── diffs/
├── tests/
└── reviews/

Rules

  • Agents never edit or delete captured evidence.
  • Gate verdicts reference evidence by path and hash.
  • Secrets are redacted before capture; evidence holds references, not credentials.
  • /gx-dev evidence opens the current run's directory.

Memory page frontmatter

Required metadata for every page in .gx-dev/memory/; structure is validated deterministically against SCHEMA.md.

---
title: Test conventions
status: verified
scope: project
freshness: 2026-08-28
sources:
  - run: gx-018
    evidence: tests/final.json
supersedes: []
---
FieldTypeRules
titlestringRequired. Human-readable page title.
statusenumdraft, verified, superseded. Unverified material stays explicitly marked.
scopestringRequired. The domain the claim applies to, e.g. project.
freshnessdateRequired. The claim's expiry contract; lint flags expired pages.
sourceslistRequired provenance: run id plus evidence reference for each claim's origin.
supersedeslistOptional. Page slugs this page replaces; contradicted pins escalate rather than drop.

Exit criteria across delivery phases

Each implementation phase exits on a machine-checkable condition, not a feeling.

PhaseExit criterion
1 · FoundationDeterministic transitions survive restart.
2 · Subagent runtimeEvery specialist runs independently with validated output.
3 · Git isolationParallel changes integrate without prematurely modifying the user tree.
4 · Research & planningApproved artifacts are versioned and hash-linked.
5 · Parallel developmentNeither worker can inspect the other's uncommitted work.
6 · Test & review loopsEvery gate transition has machine-verifiable evidence.
7 · CommitterOne traceable commit contains no unrelated changes.
8 · Compounding memoryLater workflows reuse reviewed knowledge rather than raw capture.
9 · TUI polishUsers can monitor and control a complete workflow in TUI.
10 · Documentation applicationBuild, link, responsive, theme, and accessibility checks pass.
11 · Hardening & releasenpm, Git, and local pi package installation work.
